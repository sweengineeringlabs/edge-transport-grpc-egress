This records the egress side requested by #61. It separates generic call mechanics from protocol, deployment, and security policy. The findings and comparison tables describe the assessment baseline above; the implemented outcome preserves the released egress API and is recorded in ADR-012.

## Findings

The client contract now provides `TransportInterceptor` in Pattern v0.12.0. It has a static pre-call hook that may replace `CallOptions` or reject before dispatch, and a generic, observational `on_event` callback. The migration guide specifies typed/raw unary and streaming lifecycle events. The service engine does not need to implement this contract: an egress wrapper can implement it around the opaque transport returned by the engine.

The egress interceptor API is not equivalent. `GrpcEgressInterceptor` is a runtime trait object (`Arc<dyn ...>`) with a mutable `dyn OutboundCall`; its fallible `after_call` can turn a successful unary or client-streaming response into an error. Pattern's `TransportInterceptor` is statically dispatched, its event callback cannot change an outcome, and it covers stream-open, message-read, terminal, error, and drop observations. Adopting it therefore requires a deliberate API and behavior decision, plus real-tonic integration coverage. It is not a mechanical trait rename or pure deletion.

The egress builder already follows the same caller-facing fluent shape as the client contract, the client engine, and ingress: consume `self`, return `Self` from `with_*`, then validate at `build`. Its implementation maintains another copy of seven portable transport settings before applying them to the Pattern/engine builder. An internal adapter can preserve the existing endpoint-bound egress factory and the consumer's builder calls while using the contract builder for those shared settings. The egress still needs its own state and validation for its file configuration, TLS-by-default policy, load balancing, interceptor composition, and conflicts between endpoint and backends.

## Builder comparison at the assessment baseline

| Layer | Factory and option set | Repeat/validation behavior |
|---|---|---|
| Pattern v0.12.0 | `TransportBuilder`, `RawTransportBuilder`, and `DualTransportBuilder` share `TransportConfiguration`: endpoint, TLS, connect timeout, call timeout, encoded/decoded message limits, send compression, and accepted compression. | Scalar values replace earlier values; accepted encodings accumulate idempotently. `build` rejects invalid, conflicting, missing, or unsupported values. The contract factory returns a blank opaque builder. |
| Client service v0.4.2 | `TonicTransportSpiFactory::tonic_dual_builder()` returns the Pattern dual builder plus `TonicTransportOptions`: HTTP/2 keep-alive interval, keep-alive timeout, keep-alive while idle, TCP keep-alive, TCP nodelay, concurrency limit, max idle clients, max header-list size, and user agent. | Shared options follow Pattern semantics; tonic-only values remain engine-owned. Egress uses the first three tonic options through `KeepAliveConfig`. |
| Egress `GrpcEgressBuilder` | `with_endpoint`, `with_plaintext_allowed`, `with_request_timeout`, max decoding/encoding size, send/accept compression, `with_tls`, `with_keep_alive`, `with_loadbalancer`, `with_interceptor`, `with_trace_context`, and `with_channel_config`. There is no `with_mtls` method in the current trait; mTLS arrives through `GrpcChannelConfig` and is resolved to `TlsSettings`. | Scalar setters replace values; accepted compression and interceptors append; `with_trace_context` appends an interceptor; plaintext permission is one-way. `with_channel_config` overlays endpoint/security/timeout/limits/compression/mTLS/keep-alive, with field-specific precedence. Endpoint plus load balancer and mTLS plus plaintext are rejected at `build`; zero timeout/limits and invalid targets are also rejected. |

Seven egress options overlap the Pattern contract: endpoint, TLS, request timeout (`with_timeout` at Pattern), both message limits, and send/accepted compression. `with_keep_alive` adapts to three service options. `with_channel_config` is a convenience bundle that overlaps endpoint, TLS/mTLS, timeout, both message limits, compression, and keep-alive. Plaintext opt-in, load balancing, interceptor registration, and trace propagation are egress concerns.

The egress factory is endpoint-bound (`TonicGrpcEgressBuilderSpiFactory::new(endpoint)`), then returns the domain builder through `BuildGrpcEgressBuilderRequest`. The engine factory is a zero-argument builder entry point, followed by Pattern options and tonic options. Egress can keep its existing consumer syntax: its adapter can collect egress-only policy and translate shared values to the contract builder when it constructs each backend transport. That preserves calls made by egress consumers while removing duplicate portable-option application/state only after precedence equivalence is proved. `with_channel_config` needs an explicit precedence rule before this refactor; it currently combines a bundle and individually set options, so it cannot be assumed equivalent to simple last-call-wins for every field.

Ingress #42 uses the same outer fluent shape: `GrpcIngressBuilder` consumes/returns `Self`, supports `with_*`, and ends with a validated `build`. Its scalar identity/metrics/admission options replace earlier values, routes append and duplicate route IDs fail at build, and trace context is placed first regardless of when it is configured. Egress already matches the common pattern, but its collection exceptions and bundle overlay must be documented. The two builders have different domains; no server runtime options belong in egress merely for symmetry. For shared style, use consuming `with_*`, explicit repeat semantics, and named build-time conflicts.

## Interceptor migration decision and decorator order

Pattern v0.12.0 `TransportInterceptor` is now available and specifies six lifecycle events (`Started`, `Opened`, `MessageRead`, `Completed`, `Failed`, `Cancelled`). It supports typed and raw calls with static dispatch. The client-service migration guide explicitly says no engine implementation is required solely for this contract; the egress can wrap the built dual transport.

The following compatibility differences were identified in the assessment. The decisions below were resolved for the #61 implementation:

1. **Dispatch:** egress callers currently register `Arc<dyn GrpcEgressInterceptor>`. Pattern's generic `on_event<M: MetadataView>` is not object-safe. An egress-owned runtime registry may remain behind a statically dispatched adapter, but it must not be described as direct trait adoption. The adapter and metadata views need design and compile coverage.
2. **Pre-call mutation:** egress exposes path, optional timeout, and header mutation through `OutboundCall`; Pattern receives `CallStart` and returns replacement `CallOptions`. Header/timeout behavior can be mapped, but path mutation is not offered by the Pattern hook. Confirm no required path-rewrite behavior is lost.
3. **After-call failures:** egress's `after_call` can replace a successful unary or client-streaming result with an error. Pattern lifecycle events are observation-only. Removing this capability is a behavior break for any consumer that returns an error from `after_call`; retaining it requires an egress-owned policy layer and is not covered by Pattern's interceptor contract. Existing bearer and trace implementations use pre-call behavior, but public downstream implementers are not exhaustively known.
4. **Streams:** current egress calls `after_call` only for unary and client-streaming replies. Pattern defines stream-open/read/end/error/drop events for server-streaming and bidi as well. New real-peer tests must prove each typed/raw shape, event order, metadata preservation, and exactly one terminal event.
5. **Order:** ADR-007 and the resilient integration test require egress interceptors inside retry, with breaker outside retry. Pattern does not define a chain or order. Egress must retain this explicit order and registration-order/first-error behavior.

Implemented disposition: adopt Pattern lifecycle reporting through a per-call adapter while preserving the egress runtime interceptor chain and its fallible `after_call` policy. Keep concrete interceptors, runtime registration/chain policy, bearer signing, trace propagation, retry, breaker, resilience, and load balancing in their current egress/security owners. Retry and breaker remain outside Pattern and the transport engine.

The issue #61 implementation extended mutation coverage for lifecycle reporting and its mapping boundaries, including typed/raw call shapes, stream open/read/terminal events, errors, cancellation, and runtime-chain ordering. The current manifest and results are recorded in [mutation-results.md](mutation-results.md): 128 entries, 122 caught, 6 documented expected survivors, and 0 invalid or unexplained survivors. The issue #16 scenario mutants are included in that total.

Known consumer impact:

- **This repository:** `grpc-egress-auth-bearer-std` implements the current interceptor; the transport implementation, examples, and tests use `with_interceptor`/`with_trace_context`. The transport adapter and tests now exercise Pattern lifecycle reporting; bearer signing continues to use the egress interceptor registration API.
- **JustRag:** issue [#53](https://github.com/sweengineeringlabs/justrag/issues/53) plans to use `GrpcEgressBuilderFactory`, `GrpcEgressBuilder`, `BuildGrpcEgressBuilderRequest`, and `TonicGrpcEgressBuilderSpiFactory`. The referenced migration inventory was checked at `caa0546` and had not yet adopted the builder at that snapshot. Any later adoption should preserve the builder call shape and account for the documented interceptor compatibility boundary.
- **Other released consumers:** not enumerable from this repository. Any public interceptor implementer or call site depending on `GrpcEgressInterceptor`, `OutboundCall`, `InboundReply`, or after-call failure behavior needs a breaking-change notice and migration guide. A release must not imply those users were exhaustively discovered.

Pure removal is limited to the duplicate portable-option plumbing between `GrpcEgressBuilderImpl` and Pattern's builder, if the endpoint-bound facade and all existing precedence/validation behavior are preserved. Moving the interceptor contract, changing `after_call` semantics, changing runtime dispatch, or changing decorator order is not pure removal. Retry, breaker, auth, trace, load-balancer, and resilience tests and policy do not move under this assessment.

## Accepted owner decision

The owner accepted the ownership split and authorized implementation by saying “start working” on #61. Retry/breaker/resilience, authentication, trace policy, load-balancer policy, and domain validation stay in egress/security/consumer layers. Pattern's `TransportInterceptor` supplies the pre-call identity/options and lifecycle reporting; egress retains a runtime adapter because Pattern's generic callback is not object-safe, and retains fallible `after_call` because callers can rely on it to reject unary and client-streaming replies. The egress builder facade and per-field precedence stay stable while transport construction continues to delegate to Pattern and the engine. ADR-012 records the implementation and compatibility boundary.
