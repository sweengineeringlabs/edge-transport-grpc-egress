## Phase and ownership distinctions applied

| Architecture rule | Egress interpretation | Enforcement and evidence |
|---|---|---|
| Configuration phase uses `with_<Trait>(value)` and caller-owned capabilities cross directly; it does not use request/response wrappers. | Builder/factory configuration values remain direct inputs. Do not wrap those capabilities in exposure DTOs. | Public trait inventories and external-consumer composition tests. |
| Exposure operations use `get_*`/`list_*` with operation-specific requests and owned responses. | An operation returning policy or status must have its classified request/response pair. Direct identity/property accessors stay parameterless and use Rust accessor names. | The trait matrix above classifies every method; DTO checks verify operation request/response placement and tests. |
| VOs are immutable, have value semantics (`Clone`, `PartialEq`, `Eq`) and no mutation API. User-provided VOs have public construction; response-owned configuration VOs are constructed inside their response. The architecture scanner requires VO fields private. | Retry, breaker, resilience, channel and bearer configuration are caller-supplied inputs; callers need supported constructors/builders, while struct literals and unchecked deserialization must not create invalid completed values. | Compile-fail field tests, constructor and deserialization integration tests, and the API coverage checker. |
| Response-owned configuration VOs are created internally by their response constructor. | Do not apply this visibility rule to caller-supplied configuration inputs. Preserve the distinction between a caller's policy value and a configuration value created only as response data. | Classify each VO by ownership before setting constructor visibility. |
| Phase 2 requests use `new()` for zero or fewer than three parameters and a builder for three or more. They have private fields. Build requests are construction-phase parameter bundles with intentional public fields and are explicitly exempt. Responses have private fields. | Do not blanket-wrap identity accessors or rename build requests as exposure requests. | API coverage scanner checks DTO placement and test references; doctests check private fields and constructors. |
| SAF modules are private; public factory types are canonically re-exported; implementation types stay opaque. | Consumers import root-level SAF factory exports and domain-owned traits/types. Contract types remain owned by `proto-pattern`; implementations do not duplicate them. | Compile-fail hidden-module doctests, root exports, and layout checks. |

### Export-boundary findings

All five domain crates expose their API through root-level re-exports and keep their internal `api` module private. The five implementation crates also declare `mod saf` privately and re-export their SAF factory types from the crate root, which matches the canonical factory path rule. `proto_pattern` is re-exported by transport, retry, and breaker as the contract namespace; resilient and bearer do not add that re-export.

The egress implementation previously root-re-exported `edge_security_runtime::SecurityContext` and SPI types `HealthCheck`, `HealthCheckRequest`, `HealthCheckResponse`, `HealthStatus`, `SecurityContextIdentity`, and `TokenCancellation`. Issue #60 classifies all seven paths: the health method and wire DTOs now live in the `grpc-egress-transport` domain API; the caller-specific context and cancellation adapters are implemented by consumers against `CallerIdentity` and `CancellationSignal`; `SecurityContext` is imported from its owning security crate. The egress implementation root now exposes only SAF factories. The other implementation roots expose only their SAF factories as well.

Every domain crate currently declares `pub mod` submodules beneath its private `api` module, and root-re-exports selected types. Canonical consumer paths work through root exports. Compile-fail doctests in domain and implementation crate roots prove hidden `api::...` and `saf::...` paths are inaccessible; compile-fail checks on DTOs and VOs enforce private state and constructor boundaries. The layout scanner checks domain VO fields and API/implementation placement.

### Value object invariants and construction

| Value | Validated construction and deserialization rule | Runtime/API note |
|---|---|---|
| `GrpcRetryConfig` | Positive maximum attempts; private state; deserialization routes through `try_new`. | A one-attempt policy is valid and makes no retry; defaults remain valid. |
| `GrpcBreakerConfig` | Positive thresholds/probe count; private state; deserialization validates. | `enabled` defaults true; disabled mode forwards calls without breaker admission or outcome changes. |
| `ResilienceConfig` | Composed from already validated retry and breaker policies; deserialization validates both embedded policies. | `from_policies(retry, breaker)` prevents an alternate unchecked construction route. |
| `BearerEgressConfig` | Non-empty issuer, audience and subject; positive lifetime; custom deserialization validates. | `BearerSecret::hs256` and `::rs256` reject empty key material. Secret kind is preserved in the existing serialized tagged representation. |
| `GrpcChannelConfig` | Private fields; constructor/deserialization require a non-empty endpoint, positive message size, and positive optional timeout. | Empty `Default` is only a builder seed; builders reject it as a completed endpoint config. |
| `KeepAliveConfig` | Positive interval and timeout; private fields; `Default` is valid. | No mutable accessors. |
| `MtlsConfig` | Non-empty cert/key paths and non-empty optional CA path; constructor and deserialization validate. | File contents remain checked by TLS resolution/build, which reports unusable paths. |
| `BackendTarget` | Non-empty URI and positive weight; constructor/deserialization validate. | Balancing strategy remains an upstream-compatible enum choice. |
| `LoadbalancerSettings` | Non-empty backend list; contained targets are validated; custom deserialization validates. | Configuration remains caller supplied and immutable. |

`f64` retry multipliers require an equality policy. The implementation preserves `PartialEq` semantics and implements `Eq` for the validated config value; validation rejects non-finite multipliers, so NaN cannot enter the value and reflexivity holds.
